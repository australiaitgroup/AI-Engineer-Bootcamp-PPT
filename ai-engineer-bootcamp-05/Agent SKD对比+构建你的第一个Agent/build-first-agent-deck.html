引言 & 目标

把 LLM 从"回答机"变成"会做事的助手"

单次问答之外,Agent 能让模型自主决定何时调工具、如何组合多步、何时停下给答案。它能检索文档、跑计算、调 API、查数据库,再把结果整合——这是把 LLM 工程化用于真实产品的关键一步。

02
核心概念

什么是 Agent?

一句话公式:Agent = LLM(决策器) + Tools(工具) + Planner/Executor(规划执行) + Memory(记忆) + Trace(观测)。运行模式是循环的:

Thought→ Action→ Observation↻ Final Answer
  • Thought — 模型思考:要不要调工具、调哪个、怎么传参。
  • Action — 决定后发出动作,调用某个工具。
  • Observation — 工具执行返回,作为下一轮输入。
  • Final Answer — 模型认为够了,输出最终答案。
🔁 模型负责决策,工具负责可靠执行——这个分工是理解一切 Agent 的钥匙。
03
主要构件 · 1/2

决策 · 执行 · 工具

LLM
决策器

负责思考与决策:是否调工具、调哪个、如何构造参数。Agent 的"大脑"。

Tool
工具

封装外部能力:检索、计算、HTTP API、文件读写、RAG QA。每个有 name/func/description。

Planner / Executor
规划 + 执行

Planner(或 LLM 本身)生成步骤,Executor 执行工具并把结果反馈回来。

🧩 最小 Agent 里,Planner 常常就是 LLM 自己——它边想边决定下一步,不需要独立的规划器。
04
主要构件 · 2/2

记忆 · 观测 · 刹车

Memory
记忆

会话历史或中间状态,让多步任务保持上下文。注意:会耗 token,要摘要/裁剪。

Trace / Logging
观测

记录每轮 Thought/Action/Observation,便于调试、复现与审计。

Stop Criteria
停止条件

最大步数、输出 Final Answer、超时或成本阈值——必须明确。

🛑 新手最常漏的是停止条件:没有它,Agent 可能无限循环、把外部服务打爆、账单飞涨。
05
Tool 设计要点

工具写得好,Agent 才聪明

单一职责

一个工具只做一件事,便于测试与重试。

结构化 IO

输入输出用 JSON,避免解析脆弱。

幂等性

最好可安全重试,不产生副作用累积。

权限与安全

严控写操作、shell、网络访问的权限。

错误规范

标准化错误返回,便于 Agent 判断与重试。

清晰 description

说明书写清楚,模型才知道何时用、怎么用。

🛠 反面教材:把所有逻辑塞进一个"万能工具"——既难测试、难复用,模型也搞不清什么时候该调它。
06
常见范式

三种搭 Agent 的玩法

ReAct
Reasoning + Action

交替输出 Thought 与 Action,Observation 回填,直到 Final Answer。最常用的基础范式。

Planner-Executor
先规划再执行

先生成完整步骤计划,再逐步执行,允许 Planner 中途调整。适合复杂长任务。

Tool-using Agent
能力即工具

把复杂能力(如 RAG QA)封装成单个工具,Agent 当作一个能力来调用。

🪜 本节主线用 ReAct 起步,再演示把 RAG 封成工具(Tool-using)。Planner-Executor 留给更复杂的任务。
07
安全 · 可控 · 可观测

把工具交给模型前,先系好安全带

  • 最小权限 —— 限制工具范围,每个工具只给完成任务最少的权限。
  • 记录调用 —— 记录每次工具调用与参数;敏感信息要脱敏,别记进日志。
  • 校验参数 —— 对模型生成的参数做类型、范围、白名单校验。
  • 上限 + 降级 —— 设步数与成本上限,并实现降级(缓存、返回检索片段)。
⚠️ 记住这条铁律:绝不把 shell、数据库写操作直接、无校验地开放给 Agent——这是最常见也最致命的翻车点。

实践 ① 最小 Agent

Calculator + Search,先跑通骨架

from langchain_openai import ChatOpenAI from langchain_core.tools import tool from langgraph.prebuilt import create_react_agent # 现行写法 @tool def calculator(expr: str) -> str: """计算算术表达式""" return str(safe_eval(expr)) # ⚠️ 别用裸 eval,用白名单解析 @tool def search_docs(query: str) -> str: """检索文档""" return f"docs for '{query}': [doc1, doc2]" agent = create_react_agent(ChatOpenAI(temperature=0), [calculator, search_docs]) agent.invoke({"messages": [("user", "查 X 国人口,并算它的 10%")]})
📌 更新提示:老教程的 initialize_agent(..."zero-shot-react-description") 已废弃,现用 LangGraph 的 create_react_agent,内部同样是 ReAct 循环。

实践 ② RAG 封装为工具

让 Agent 能直接"查文档"

from langchain_core.tools import tool @tool def document_qa(question: str) -> str: """用已上传文档回答问题,返回带来源的答案""" return rag_qa(question) # 调用你自己的 RAG pipeline # -> "Answer: ... Sources: [file.pdf#p3]" agent = create_react_agent(llm, [document_qa]) agent.invoke({"messages": [("user", "总结项目排期的关键点")]})
✅ 好处:把"检索 + 生成"这一整套复杂能力,收拢成一个工具。Agent 只需把"文档问答"当作一种能力来调用,便于组合更复杂任务(如先查证再生成报告)。

实践 ③ 带记忆的多步 Agent

让它记住上一句

from langgraph.checkpoint.memory import InMemorySaver # 用 checkpointer 保存会话状态(现行做法) agent = create_react_agent(llm, tools, checkpointer=InMemorySaver()) cfg = {"configurable": {"thread_id": "user-1"}} # 同一 thread 保持上下文 agent.invoke({"messages":[("user","查产品 A 的销售数据")]}, cfg) agent.invoke({"messages":[("user","和上个月对比一下")]}, cfg) # 用记忆保持上下文
🧠 记忆的代价:会话越长越占 token。生产里要做摘要或裁剪,别让上下文无限膨胀又慢又贵。

实践 ④ 自实现 ReAct Loop

掀开引擎盖,看清底层

def react_loop(question, max_steps=6): history = PROMPT_HEADER + f"\nQuestion: {question}\n" for _ in range(max_steps): # ← 停止条件 out = call_llm(history) typ, tool, arg = parse_action(out) # 正则解析 Action/Final if typ == "final": return tool if typ == "action": obs = TOOLS.get(tool, unknown)(arg) history += out + f"\nObservation: {obs}\n" return "Stopped: reached max steps"
🔧 自实现的价值:透明、好调试,你能完全掌控解析、执行、重试。代价是解析脆弱、安全要自己兜——生产别用裸 eval,用白名单/沙箱。
13
最佳实践

让 Agent 能真正上生产

① 工具有清晰 contract

单一职责 + JSON schema 输入输出。

② 严格校验 + 白名单

限制权限,避免任意执行。

③ 记录完整 Trace

T/A/O 全留痕,便于复现审计。

④ 设停止条件

最大步数/超时/成本上限,防失控。

⑤ 幂等 + 重试退避

合理的错误返回与退避策略。

⑥ 高风险加 verifier/审批

输出前用规则或另一模型核验关键断言。

⑦ 沙箱 + 攻击模拟

用畸形/恶意输入测校验能否兜住。

⑧ 监控成本 + 逐步放权

调用限额告警;先受控环境再上生产。

14
常见陷阱

这些坑,基本人人踩过

  • 危险能力直接开放 —— 把 shell / 数据库写入直接给 Agent,极易被滥用。
  • 不校验就执行 —— 直接跑模型生成的参数,容易注入或异常。
  • 没有停止条件 —— 导致无限调用工具、费用暴涨。
  • 忽略日志 —— 出问题后无法追踪 Agent 的决策流程。
  • 万能工具 —— 把所有逻辑塞进一个工具,难测试难复用。
  • 过度自动化 —— 高风险场景不留人工复核。
🧭 一句话:先假设 Agent 会犯错、会被攻击,再来设计权限、校验和日志——防御式设计,而非事后补救。

16
小结

带走这四句话

  • Agent = 会思考的 LLM + 会做事的工具:模型负责决策,工具负责可靠执行。
  • 关键四件事:定义好工具(单一职责/结构化/幂等)、清晰的 T/A/O 格式、停止与安全策略、每次调用都日志+校验。
  • 从小做起:先 Calculator+Search,再把 RAG 封成工具,最后加 memory、verifier 与监控。
  • 上生产前提:安全、可重试、可追溯、成本控制与严格测试,缺一不可。
