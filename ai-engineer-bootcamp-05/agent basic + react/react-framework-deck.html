ReAct:让模型
边想边做

把推理(Reasoning)和行动(Action)交替组合成一个循环决策流程。模型不再一次性吐答案,而是:出声思考 → 调工具 → 看结果 → 继续想……直到给出可查证的最终答案。

Thought→ Action→ Observation↻ Final Answer
零基础 · AI Engineer 训练营 01
引言

从"回答机"到"会查会算的 Agent"

传统把 LLM 当"回答机",一次性生成答案——不会查证、算不准、碰不到外部世界。ReAct 把模型的强推理,接上工程世界的可执行能力。

传统用法
一次性回答
  • 问一句答一句,无中间过程
  • 容易"自信地编",无法查证
  • 不能调用搜索/计算/数据库
ReAct
推理↔行动 闭环
  • 可观察的推理(Thought)逐步展开
  • 需要时发动作(Action)调工具
  • 把观测(Observation)喂回继续推理
🎯 适用场景:多步决策、查证事实、需要外部工具与闭环验证——例如 RAG + 事实核验、复杂问答、自动化任务。
02
核心概念

三要素:Thought / Action / Observation

Thought
思路 · 内部语言

模型每一步产生的推理。要可读,这样你才能调试、看清它在想什么。

Action
行动 · 调用工具

需要外部能力时发出动作,含工具名+参数,如 Action: Search["climate 2024"]。

Observation
观测 · 工具返回

工具执行后的结果,作为下一轮推理的输入。

User input→ Thought→ Action→ Observation→ Thought…→ Final Answer
🔁 三要素交替转圈,直到模型认为够了,输出 Final Answer。这就是 ReAct 的全部骨架。
03
走一遍轨迹

一个 ReAct 循环长什么样

问题:"加拿大人口的 15% 大约是多少?"——需要先 Search 查人口,再 Calculator 算百分比。

Thought: 我需要先查加拿大人口 Action: Search["population of Canada"] Observation: 约 4,100 万 Thought: 现在算它的 15% Action: Calculator["41000000 * 0.15"] Observation: 6150000 Thought: 已得到结果,无需再调工具 Final Answer: 约 615 万(基于人口约 4,100 万)
💡 注意每一步都"留痕":Thought 让你看清推理,Action/Observation 让你看清它调了什么、拿到啥。这套轨迹就是天然的调试日志。
04
核心概念 · 工具

Tools:Agent 能调用的"手"

工具 = 外部能力:检索(search/RAG)、计算器、HTTP API、数据库、文件系统,甚至另一个模型或微服务。

每个工具三件套
  • name — 供模型引用的名字
  • description — 明确用途,模型靠它判断何时用
  • func — 真正执行的函数
好工具的特征
  • 单一职责 — 一个工具只干一件事
  • 幂等 — 可安全重试
  • 结构化输出(JSON) — 便于模型解析
🛠 工具的 description 是 Agent 的"说明书":写得含糊,模型就会用错工具名、传错参数,Agent 立刻变笨。
05
核心概念 · 格式化

严格的交互格式 = 稳定的解析

给模型一个严格的输出模板,既能提升它的稳定性,又方便你的程序端解析输出、执行对应动作。

You are an assistant that alternates between Thought, Action, Observation. Use tools only when needed. Format exactly: Thought: <what you are thinking> Action: <ToolName>[arguments] Observation: <result from tool> ... repeat. When done: Final Answer: <concise answer with sources> Available tools: - Search: use to look up facts - Calculator: do arithmetic
📐 "Format exactly" 很关键:格式越严格,后面用正则/解析器提取 Action 越可靠。格式自由 = 解析脆弱。
06
停止条件 & 可控性

一定要有"刹车"和"黑匣子"

🛑 停止条件(必须有)
  • 固定最大步数(如 6 步)
  • 模型输出 Final Answer: 即停
  • 超时 / 成本阈值触发降级
🔍 可观测 & 可控
  • 每步 Thought/Action/Observation 存为 trace
  • 限制工具权限,明确输入/输出 contract
  • 便于调试、审计,规避安全/隐私风险
⚠️ 没有停止策略 = 无限循环 + 烧钱 + 把外部服务打爆。停止条件不是可选项。
07
实战 A · 快速上手

用框架:几行就能跑起来

主流框架已内置 ReAct 风格交互,你只需定义工具 + 一行初始化。打开 verbose 就能在控制台看到 Thought/Action/Observation。

# 定义两个工具 tools = [ Tool(name="Search", func=search_tool, description="查事实"), Tool(name="Calculator", func=calc_tool, description="做算术"), ] # 现代写法:LangGraph 的 create_react_agent from langgraph.prebuilt import create_react_agent agent = create_react_agent(llm, tools) agent.invoke({"messages": [("user", "法国人口的 10% 是多少?")]})
📌 注意:老教程里的 initialize_agent(..."zero-shot-react-description") 已废弃,现以 LangGraph 的 create_react_agent 为准。原理不变,接口换了。
08
实战 B · 透明可控

自己实现:看清每个齿轮

不靠框架,纯 Python 手写一个 ReAct loop——你能完全掌控解析、工具调用、记录与重试。理解细节,从这里开始。

def react_loop(query, max_steps=6): history = PROMPT_HEADER + f"\nQuestion: {query}\n" for step in range(max_steps): # ← 停止条件:最大步数 out = call_llm(history) typ, tool, arg = parse_action(out) # 正则提取 Action / Final if typ == "final": return tool # 拿到 Final Answer,收工 elif typ == "action": obs = TOOLS.get(tool, unknown)(arg) # 执行工具 history += f"\n{out}\nObservation: {obs}\n" # 回填观测 return "Stopped: exceeded max steps" # 触发刹车
🔧 自实现的代价:解析脆弱(自由文本难解析)、安全要自己兜。生产里绝不要用 eval 跑模型给的表达式——用白名单或沙箱。
09
最佳实践 · 上

让 ReAct Agent 稳下来(1/2)

① 明确工具清单与描述

prompt 里列清可用工具与用途,减少模型误用工具名/参数。

② 结构化 IO

工具返回 {"status":"ok","result":…},后续解析更可靠。

③ 限制步数与成本

设最大步数 + token/成本上限,防失控。

④ 记录完整 trace

每轮 T/A/O 落日志(或 LangSmith/Langfuse),便于审计调优。

⑤ 幂等与重试

工具可安全重试,对外请求做退避 + 抖动。

⑥ 输入校验与沙箱

绝不把可执行代码随意丢进 eval,用白名单/沙箱。

10
最佳实践 · 下

让 ReAct Agent 稳下来(2/2)

⑦ 测试覆盖

为正常路径、失败路径、边界情形写单测,尤其是工具解析与异常处理。

⑧ 加 verifier / validator

最终输出前,用规则或另一个模型核验关键断言(fact-check)。

⑨ 设计可解释的 Thought

鼓励模型输出清晰、简短的 Thought,方便人理解与干预。

⑩ 逐步放开权限

先在 sandbox 里测 agent + 工具,再到高权限环境放开功能。

🧭 这十条的共同主线:结构化 + 有上限 + 可追踪 + 先沙箱后放权。和"上生产"那节完全一脉相承。
11
常见陷阱

这些坑,基本人人踩过

  • 无限循环 —— 没停止条件,或模型反复调同一个工具兜圈子。
  • 过度信任模型生成的指令 —— 工具名/参数可能是错的,必须验证。
  • 安全漏洞 —— 把 shell、数据库写操作直接开放给 agent,极易被滥用。
  • 没有监控与审计 —— 一旦 agent 做错事,无 trace 就很难定位原因。
  • 解析脆弱 —— 正则解析自由文本容易失败,尽量用严格格式 / OutputParser。
  • 成本失控 —— 频繁调用高成本 LLM/工具却没有预算控制。
⚠️ 还有一个隐性坑:工具耦合过深——一个工具干太多事,既难维护又难重试。回到"单一职责"。
12
动手练习

从 mini-Agent 到加验证层

① 实现 mini-Agent

带 Search + Calculator 两个工具,解决:"加拿大人口的 15% 约是多少?"(先查再算)。

② 封装 RAG 工具

把现有 RAG QA 封装成 DocumentQA 工具,实现"先检索文档再总结"。

③ 加上 verifier

给出 Final Answer 前,调 FactCheck 工具核验关键断言,不确定就标注。

④ 实现 trace 记录

每步 T/A/O 存成 JSON,再写小脚本按序可视化整条轨迹。

🎯 循序渐进:先 Calculator+Search 跑通骨架,再逐步纳入 RAG/DB/HTTP,并加验证层,让 Agent 越来越稳。
13
小结

带走这四句话

  • ReAct = 透明推理(Thought) + 可执行动作(Action) + 观测(Observation) 交替成环,适合工具调用 + 多步决策。
  • 四个关键:清晰的交互格式、可靠的工具接口、稳定的停止条件、良好的可观测性。
  • 工程四要点:安全、可重试、成本控制、审计能力——生产前充分测试 + 沙箱验证。
  • 从小做起:Calculator + Search 起步,逐步纳入复杂工具并加验证层,让 Agent 稳健可信。
🚀 一句话:ReAct 不神秘——它就是给 LLM 装上"出声思考"和"动手能力",再套进一个有刹车、有黑匣子的循环。
