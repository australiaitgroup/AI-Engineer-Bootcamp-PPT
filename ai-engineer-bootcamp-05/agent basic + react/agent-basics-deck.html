直播课 · Agent 工程

Agent 不是魔法
是 LLM 套在循环里

很多人被 LangChain 文档绕晕。其实搞清一条就够:Agent = LLM + 工具调用 + 一个外层 while 循环,剩下全是包装。这节从最小可运行的计算器 Agent 开始,看 LLM 怎么决定调哪个工具、拿到结果后怎么接着推理。

LLM

会思考、会生成文本的大脑。

+ 推理

分析现状、决定下一步。

+ 工具

能真正去执行操作。

+ 记忆

记住上下文,持续推进。

理解骨架 > 背十个框架名词 01
一句话定义

LLM 只会说,Agent 会做

最关键的一条分界线:LLM 拿到问题,只能生成文本回答你;Agent 在 LLM 外面套了循环和工具,于是它能执行操作——查资料、算数、调 API、改文件,再根据结果继续。

纯 LLM
只能生成文本
  • 你问,它答,一问一答到此为止
  • 不能上网、不能算大数、不能动外部世界
  • "我没法访问实时数据"——就是它的天花板
Agent
LLM + 推理 + 工具 + 记忆
  • 会判断"这一步该调哪个工具"
  • 能真正执行:搜索、计算、调接口、写文件
  • 拿到结果接着推理,直到任务完成
🧠 公式记牢:Agent = LLM + 推理 + 工具调用 + 记忆。少了"工具"它就退回成聊天机器人,少了"循环"它就只能走一步。
02
核心机制

Agent 的核心循环

把所有花哨框架剥掉,内核就是这个 while 循环:想 → 决定 → 执行 → 更新上下文,循环到任务完成。

while not done: thought = llm.think(context) # 1. 想:基于当前上下文推理 action = llm.decide(thought) # 2. 决定:选哪个工具、传什么参数 result = execute(action) # 3. 执行:真正去调用工具 context = update(context, result) # 4. 更新:把结果塞回上下文,进入下一轮
🔁 关键:每一轮 LLM 都能看到"上一步干了什么、拿到什么结果",于是它能自我纠错、逐步逼近答案——这正是 Agent 比单次问答强的地方。
03
拆开看

一轮循环里发生了什么

1
Think
想

读当前上下文,推理"现在到哪了、还差什么"。

2
Decide
决定

选出要调的工具,以及传给它的参数。

3
Execute
执行

你的代码真正运行那个工具,拿回结果。

4
Update
更新

把结果写回上下文,判断完成没——没完就回 ①。

💡 谁做什么:Think / Decide 是 LLM 干的(动脑),Execute 是你的代码干的(动手)。LLM 永远不直接碰外部世界,它只是"发指令"。
04
最小可运行例子

一个计算器 Agent 的骨架

# 工具箱:Agent 能调用的"手" tools = {"add": lambda a,b: a+b, "mul": lambda a,b: a*b} def agent(question): context = [{"role":"user","content": question}] while True: reply = llm(context, tools=tools) # LLM 想 + 决定 if reply.tool_call: # 它要调工具 name, args = reply.tool_call result = tools[name](**args) # 你的代码执行 context += [reply, {"role":"tool","content": result}] # 更新 else: return reply.text # 没有工具调用 = 给出最终答案
🧮 例子:问 "(3+4)×5 等于多少?" → LLM 先调 add(3,4)=7 → 看到 7 再调 mul(7,5)=35 → 没工具可调了,输出 "35"。整个过程就是上面那个 while 循环转了两圈。
05
关键区分

Agent vs Chain:差在"谁做决定"

两者都把多步骤串起来,但本质区别是:流程是你写死的,还是让 LLM 临场决定的。

维度Chain(链)Agent(智能体)
执行流程固定顺序,A→B→C 写死动态决策,下一步临场定
工具选择预定义,什么时候用哪个都安排好LLM 自主选择该调哪个
循环一般跑一遍就结束while 循环,跑到完成为止
可预测性高,每次走法一样低,每次可能不同
适合步骤明确、可重复的流程路径不确定、需随机应变
⚖️ 一句话:Chain 是你定路线让 LLM 沿着走;Agent 是给 LLM 地图和工具,让它自己找路。
06
别一上来就 Agent

什么时候才真的需要 Agent?

Anthropic 的建议很实在:先找最简单的方案,只在必要时才加复杂度。 Agent 灵活,但也更慢、更贵、更难预测、更难调试。

✅ 用 Agent
  • 路径事先说不清,要看中间结果才知道下一步
  • 需要在多个工具间灵活选择
  • 任务开放、步数不固定
❌ 别用 Agent(用 Chain/Workflow)
  • 流程固定、可重复,每次都一样
  • 要求结果稳定可预测、好排错
  • 对延迟和成本敏感
📌 反直觉但重要:能用固定 workflow 解决的,就别上 Agent。 把 Agent 留给"真的需要临场决策"的场景。
07
工具调用 · 原理

LLM 怎么"调用"工具?

LLM 本身只会生成文本——它并不会真的执行代码。所谓工具调用,是 LLM 输出一个结构化的"调用请求",由你的代码去执行,再把结果喂回去。

1
给工具说明书

把每个工具的名字、用途、参数(JSON schema)告诉 LLM。

2
LLM 发请求

它判断要用哪个,输出 {tool, args} 而不是直接答。

3
你执行+回填

代码运行工具,把结果作为新消息塞回上下文。

🛠 工具写得好不好,直接决定 Agent 聪不聪明:名字清晰、描述明确、参数简单。工具描述含糊,LLM 就会乱调或不调。
08
记忆 · Memory

没有记忆,Agent 走一步忘一步

"记忆"本质就是那个不断累积的 context。每轮把动作和结果追加进去,LLM 下一轮才知道前因后果。但上下文有限,所以要会管理。

短期记忆
working context

当前任务的对话和工具结果,直接放在 context 里随轮次累积。

长期记忆
external store

跨会话要记住的东西,存到向量库/数据库,需要时检索回来。

上下文管理
不能无限塞

窗口有限:旧内容要摘要、裁剪或检索,否则又慢又贵还会丢重点。

🧩 实战提醒:context 不是越长越好。塞太多无关信息,LLM 反而会"分心"——精心挑选放进去的内容,是 Agent 工程的核心功夫。
09
常见 Agent 模式

四种最常见的玩法

它们不是互斥的,而是一层层叠上去:从"边想边做",到"配工具",到"先规划",再到"多 Agent 协作"。

ReAct
Reason + Act

推理一步、行动一步,交替进行——最常用的基础模式。

Tool Use
配备工具

给 Agent 一个工具箱,让它按需调用搜索、计算、API。

Planning
先规划再执行

先把任务拆成计划,再逐项落地,适合复杂多步任务。

Multi-Agent
多 Agent 协作

多个各有分工的 Agent 协同,一个总控分发、其余执行。

🪜 学习顺序建议:先吃透 ReAct + Tool Use(本节重点),再按需要往 Planning 和 Multi-Agent 升级。别一上来就堆多 Agent。
10
模式 ① ReAct

Reasoning + Acting:边想边做

ReAct 让 LLM 把"思考"显式地说出来,再行动,再观察结果,再思考……就是核心循环加上"出声思考"。

# ReAct 的典型轨迹(Thought / Action / Observation 交替) Thought: 用户问 (3+4)×5,我得先算括号里的加法 Action: add(3, 4) Observation: 7 Thought: 现在拿 7 去乘 5 Action: mul(7, 5) Observation: 35 Thought: 已得到答案,不需要再调工具 Answer: 35
🗣 "Thought" 出声思考的好处:LLM 推理更稳、你也能看清它每一步在想什么,排错和加 guardrails 都更容易。
11
模式 ② Planning

先规划,再执行

任务复杂、步数多时,与其走一步看一步,不如让 Agent 先列出整体计划,再逐项落地,必要时回头修订计划。

先 Plan
  • 把大任务拆成有序子步骤
  • 看清依赖关系、需要哪些工具
  • 减少"走偏了一大截才发现"的浪费
再 Execute
  • 按计划逐项执行,每步可验证
  • 结果不符预期时,回头改计划
  • 适合写代码、做研究等长链路任务
🗺 代价:多了"规划"这步会更慢、更贵。简单任务别强行 Planning,ReAct 就够。
12
模式 ③ Multi-Agent

多 Agent 协作:分工与协调

把一个大任务拆给多个各有专长的 Agent:常见是一个总控(Orchestrator)负责分发和汇总,若干子 Agent各管一块。

Orchestrator
总控/协调

拆任务、分发给子 Agent、汇总结果。

Worker Agents
各司其职

每个只负责一块,如"检索""写作""校对"。

代价
别滥用

更复杂、更贵、更难调试,Agent 间还会"沟通失真"。

⚠️ 忠告:多 Agent 看着酷,但大多数任务用单 Agent + 好工具就够了。只有当任务能清晰拆成并行的、互不干扰的子任务时,多 Agent 才划算。
13
动手练习

写出你的第一个计算器 Agent

不用任何框架,纯手写,目标是把"LLM + 工具 + while 循环"这条骨架跑通。

① 定义两个工具

写 add(a,b) 和 mul(a,b),并给每个写清楚名字和参数说明。

② 写外层 while 循环

实现 think→decide→execute→update,直到 LLM 不再调工具。

③ 喂一道两步题

问 "(3+4)×5",观察它调了几次工具、每次调了啥。

④ 打印每一轮

把每轮的 thought / action / result 打出来,亲眼看见循环转动。

🎯 目标不是写得多花哨,而是亲手看见 LLM 自己决定调哪个工具、拿到结果后怎么接着推理——这个"啊哈"时刻比读十篇文档都值。
14
常见误区

新手最容易踩的几个坑

  • "Agent 很神秘" —— 不,它就是 LLM + 工具 + while 循环,框架只是包装。
  • "什么都用 Agent" —— 流程固定的任务用 Chain/Workflow 更稳更便宜。
  • "工具随便写写" —— 工具描述含糊,LLM 就会乱调或不调,Agent 立刻变笨。
  • "上下文越长越好" —— 塞太多反而分心、又慢又贵,要会摘要和裁剪。
  • "先上 Multi-Agent 才高级" —— 单 Agent + 好工具能解决的别复杂化。
🧭 一条总原则:从最小骨架开始,需要时才加复杂度。 先让计算器 Agent 跑通,再谈别的。
15
小结

带走这三句话

  • Agent = LLM + 推理 + 工具调用 + 记忆,内核是一个 think→decide→execute→update 的 while 循环。
  • Agent 与 Chain 的区别在"谁做决定":Chain 走你定好的路,Agent 自己临场找路;能用 Chain 就别上 Agent。
  • 四种模式层层叠加:ReAct → Tool Use → Planning → Multi-Agent;先吃透前两个,其余按需升级。
